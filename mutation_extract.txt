3.4.5 Mutation Testing of Scoring Logic
Mutation testing was applied as a fifth validation method to evaluate the sensitivity of the
behavioural test suite for the scoring engine. Mutation testing, introduced by DeMillo,
Lipton, and Sayward [26] and surveyed by Jia and Harman [27], evaluates a test suite by
introducing small artificial changes to the source code and rerunning the tests. Each modified
version of the code is called a mutant. If at least one test fails on the mutated code, the
mutant is killed, indicating that the test suite detected the behavioural change. If all tests
still pass, the mutant survives, indicating a behavioural change that the tests fail to detect.
The ratio of killed mutants to the total number of non-equivalent mutants is the mutation
score. Mutation testing literature reports that mature test suites typically achieve mutation
scores in the 60 to 80 percent range [27].
The technique was scoped to the scoring domain on methodological grounds. The scoring do-
main is deterministic, contains no I/O or external dependencies, and consists of pure business
logic, which makes it the most reliable target for mutation analysis. It is also the canon-
ical instance of architectural requirement R1, centralized domain logic. Mutation testing
therefore complements the other validation methods rather than duplicating them: import-
linter verifies architectural conformance, the pytest suite verifies functional behaviour, and
mutation testing probes the strength of the functional tests themselves.
The tool used wasmutmut. The outcomes are reported in Section 4.4.5.

The project was managedusingan agile approachbased on the Kanban method [28]. Kanban
was chosen over Scrum because the workload was non-uniform across the semester. Early
work focused on problem analysis, literature review, and architectural design, while later

The agile method was used as a project-execution method, not as the analytical core of
the thesis. The academic method of the thesis was the design and validation of a software
artefact.

5.2 Validity of the Validation Approach
The conclusions in Section 5.1 depend on the validity of the validation approach itself. Three
threats to validity are present, and they differ in severity.
The most serious threat is that the architectural requirements, design decisions, and valida-
tioninstrumentswereallproducedandevaluatedbythesameteam, whichintroducestherisk
that the validation methods were designed to confirm the architecture rather than to chal-
lenge it. Two partial mitigations apply. First, the structural validation tools, import-linter
and AST-based analysis, operate through independent mechanisms and were configured sep-
arately, so a false positive from confirmation bias would have to appear in both parallel
sets of contracts, which is substantially harder than in one. Second, the Schemathesis run
reported in Section 4.4.4 derives test cases from the OpenAPI document using an externally
authored tool, so for R2 specifically the tests themselves are not products of the team. Nei-
ther mitigation eliminates the underlying risk, because the team still selected which tools
to apply and which contracts to encode; a stronger study would have an external software
architect define the contracts before implementation began.
The second threat concerns the behavioural test suite that supports R1. The suite covers
seven distinct properties of the scoring engine but does not constitute exhaustive coverage of
all domain logic in the system. The service interval engine and the normalization layer were
not subjected to the same level of behavioural testing. This is a coverage gap rather than
a methodological flaw: the tests that exist are valid, but additional tests would strengthen
the evidence for R1 across all backend components. Mutation testing of the scoring do-
main (Section 4.4.5) both strengthens and qualifies this part of the validity argument. It
strengthens the argument because the behavioural tests are themselves probed rather than
trusted: 365 of 1185 mutants were detected, providing direct evidence that the tests respond
to behavioural change in the scoring logic. It qualifies the argument because the resulting
mutation score of 30.8 percent is below the 60 to 80 percent range reported as typical of
mature test suites. Two considerations frame how this result should be interpreted. First,
the behavioural test suite was scoped to verify the seven specific properties listed in Sec-
tion 3.4.2: determinism, runtime isolation, grade-boundary mapping, confidence dampening,
the directional effect of good maintenance, the effect of severe unrepaired incidents, and the
relative penalty for repaired versus unrepaired incidents. The suite was therefore designed as
a property-based check on R1 rather than as an exhaustive functional specification of every
scoring rule. The mutation score reflects this scope: the tests detect changes that affect
the properties they target, and survive changes that do not. Second, extending the suite to
raise the mutation score was not pursued in the available project time. Strengthening the
suite is a direct continuation of the existing approach and would not require any architec-
tural change, since the scoring engine is already isolated as a pure domain module. This
extension is identified as future work in Section 7.4. The overall threat is acceptable for a
bachelor-scope prototype and represents a direct extension for future work.

7.3 Limitations
The OBD-II reading pipeline was implemented and validated on two physical vehicles, a
Mazda 3 and a Toyota Yaris, using a real ELM327 Bluetooth adapter. Signal decoding is per-
formed on-device prior to backend upload, as the BLE transport does not permit raw frame
forwarding to a remote endpoint. The DTC description lookup is currently implemented
as a hardcoded client-side map; codes absent from the map are displayed as ÔÇ£Unknown di-
agnostic trouble code,ÔÇØ as encountered with codes P0221 and B1622 during testing on the
Toyota Yaris. Relocating the DTC lookup to the backend remains an identified direction for
future work.
Receipt scanning was implemented as an exploratory prototype extension in which receipt
images are uploaded from the mobile client and processed by the backend using OCR to sug-
gest candidate maintenance fields for user review. However, this feature was not included in
the formal validation of unified multi-source maintenance history, and manual entry remains
the primary validated non-diagnostic input source in the current prototype.
No usability testing was conducted with real users, which means the systemÔÇÖs effectiveness
from a user experience perspective remains unevaluated. The architectural requirements,
design decisions, and validation instruments were all produced and evaluated by the same
team, introducing the risk that the validation approach was designed to confirm the archi-
tecture rather than to challenge it. Additionally, the system does not enforce verification of
vehicle ownership at registration.
Mutation testing of the scoring domain achieved a mutation score of 30.8 percent. The
behavioural test suite detects grade-boundary changes and broad directional properties but
does not fully specify confidence-threshold behaviour, normalization behaviour, maintenance
interval scoring, documentation-quality scoring, or the exact category and overall score cal-
culations. A total of 204 mutants had no associated tests. Of these, 202 were in normalize.py
and 2 were in engine.py. The implications of this for R1 validity are discussed in Section 5.2,
and the concrete extension is identified in Section 7.4.
7.4 Future Work
Relocating the DTC description lookup from the mobile client to a dedicated backend service
would restore full thin client conformance for the OBD-II feature and allow the diagnostic
code database to be extended without requiring a client release. Two approaches are vi-
able. The first is a static backend DTC database mapping standard SAE and manufacturer
codes to plain-language descriptions; this approach guarantees deterministic output and is
straightforward to extend incrementally. The second is an LLM-powered diagnostic service
that receives the decoded DTC codes alongside relevant vehicle metadata such as make,
model, year, and engine type, and generates contextual explanations either from training
data or via retrieval-augmented search. Such a service could produce richer, vehicle-specific
descriptions than a static map, but introduces non-determinism and dependency on an ex-
ternal model. A static database is the more appropriate first step given the accuracy require-
ments of diagnostic information; an LLM-based service represents a viable extension once
a reliable baseline is established. Because the backend is already organised as a modular
layered system, either approach could be introduced as an isolated domain service without
affecting the existing API contract or client applications.
Strengthening the scoring test suite to address the gaps revealed by mutation testing in
